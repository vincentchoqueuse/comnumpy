# Third-party reference data: pyldpc

Files here are **generated by** [pyldpc](https://github.com/hichamjanati/pyldpc)
(Hicham Janati), not copied from it: they are the decisions its
sum-product decoder returns on a channel this project defines. No pyldpc
source code is redistributed, and nothing here goes in `src/`.

A note on its licence, because the two statements disagree. The package
metadata declares `License: MIT`, while the `LICENSE` file shipped inside
the distribution -- reproduced here as `LICENSE.BSD-3-Clause` -- is
BSD-3-Clause. The file is the more specific of the two, so it is the one
honoured. Both are permissive and compatible with this project's MIT
licence, so the discrepancy changes nothing in practice; it is recorded
rather than smoothed over so that anyone redistributing downstream can
reach their own conclusion instead of inheriting ours. As with the GNPy
data, no endorsement by the author is claimed or implied.

| File | What it is |
|---|---|
| `ldpc_parity_check.csv` | The (96, 50) regular Gallager matrix both decoders are given, one row of bits per parity check |
| `ldpc_reference.csv` | Per SNR and per word: the transmitted codeword and the codeword pyldpc's sum-product decoder returned |
| `ldpc_manifest.csv` | The seed, the code parameters, pyldpc's version and BER per point, and a SHA-256 of the log-likelihood ratios |
| `generate_ldpc_reference.py` | The script that produced the three above |

## Why the matrix is shipped, and why that is the point

The usual obstacle to validating an LDPC decoder against the literature
is that published curves rarely come with the exact parity-check matrix
behind them. A disagreement can then always be blamed on the code rather
than on the decoder, which makes the comparison unfalsifiable.

Sharing the matrix removes the obstacle. Both decoders receive the same
H **and** the same log-likelihood ratios, so the only difference left is
the check-node update -- min-sum here, sum-product there -- and any
disagreement is attributable to it alone.

## Why a seed rather than the samples

The channel is regenerated from `seed` instead of being shipped sample by
sample, which keeps the reference to a few kilobytes. That is only sound
because the stream is stable, and it was checked rather than assumed:
`default_rng(seed).standard_normal` gives bit-identical output under
numpy 1.26.4 and 2.4.6, the floor and the newest release this project
supports.

`llr_sha256` is the guard. If a future numpy changes the stream, the
replayed channel stops matching the recorded hash and the validation
fails loudly, instead of quietly comparing two decoders on two different
channels and reporting the difference as a decoder disagreement.

## Reproducing

```bash
pip install --no-build-isolation pyldpc   # its setup.py imports numpy
                                          # without declaring it as a
                                          # build requirement
python validation/data/pyldpc/generate_ldpc_reference.py
```
